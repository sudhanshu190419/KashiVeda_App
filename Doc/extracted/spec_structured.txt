[TBL] (1 rows)
  | Architecture decision: Phase 1 uses a Supabase-native backend. No Fastify or Drizzle layer is required for the approved scope. Supabase PostgreSQL is the system of record; Supabase Auth, RLS, Storage, Realtime, Edge Functions, Cron, Queues and PostGIS provide the backend platform services. External providers such as Razorpay, WhatsApp and the selected live-video service are integrated through server-side Edge Functions.

[P] 1. Architecture Decision
[P] This revision supersedes the earlier ERD implementation assumption that migrations would be generated from Drizzle. The entity model remains relational, but the execution model is Supabase-native.
[P] Client applications: React Native mobile apps, customer-facing website and Admin web portal.
[P] Authentication: Supabase Auth.
[P] Database: Supabase PostgreSQL.
[P] Normal data access: Supabase client/PostgREST under RLS.
[P] Atomic business operations: PostgreSQL functions/RPCs called through authenticated server/client flows as appropriate.
[P] Privileged and third-party operations: Supabase Edge Functions with server-side secrets.
[P] File storage: Supabase Storage with private buckets and signed URLs for sensitive documents.
[P] Realtime: Supabase Realtime; durable state lives in PostgreSQL. Prefer Broadcast for ephemeral events and avoid subscribing to every table change.
[P] Scheduled work: Supabase Cron.
[P] Reliable asynchronous work: Supabase Queues for retryable/background processing.
[P] Geospatial filtering: PostGIS for Pandit service areas and customer-location matching.
[P] Migrations: Supabase SQL migrations managed with the Supabase CLI and committed to Git.
[P] The older product blueprint proposed Fastify and Drizzle, but this document intentionally replaces that implementation choice. The final Phase 1 business behavior remains the controlling requirement.
[P] 2. Supabase-Native System Architecture
[P] Figure 1. Supabase-native Kashi Veda domain architecture.
[P] 2.1 Runtime responsibilities
[P] Frontend clients may read/write only through authenticated Supabase APIs and RLS-protected operations.
[P] Client applications must never contain a Supabase service-role key, Razorpay secret, WhatsApp credential, live-provider secret or payout credential.
[P] Price calculation, booking confirmation, refunds, payout eligibility and other money/state transitions must be validated server-side in PostgreSQL functions and/or Edge Functions.
[P] PostgreSQL remains the source of truth for booking and payment state; client UI state is never authoritative.
[P] Storage paths and signed URLs are controlled by database authorization rules; customers and Pandits only receive files they are entitled to access.

[P] 6.3 Realtime, Cron and Queues
[P] Realtime Broadcast: use for ephemeral booking/availability/live-session UI events where subscribers need immediate updates but the event itself is not the source of truth.
[P] Postgres Changes: use selectively for durable notification badge updates or narrowly scoped state changes; do not subscribe every client to high-churn tables.
[P] Cron: daily subscription deactivation, scheduled astrology generation/delivery, reminders and housekeeping.
[P] Queues: retryable WhatsApp/push delivery, batch astrology delivery, deferred payout work and other asynchronous jobs.
[P] The database remains authoritative even when a realtime or queue message is delayed or duplicated; consumers must be idempotent.

[P] 8. PostGIS / Pandit Location Matching
[P] Pandit service areas are stored as normalized location records and/or PostGIS geography values.
[P] Customer home-visit booking validates that the selected Pandit serves the customer location before a slot can be confirmed.
[P] A Pandit may be shown publicly as “Currently Unavailable” even when the profile remains visible; availability and service-area checks are separate concerns.
[P] A booked slot is excluded from future availability blocking so a Pandit cannot accidentally make an existing booking unavailable.
[P] Spatial indexes should be added for the chosen geography columns if radius-based search is used.

[P] 11. Money, Payment and Payout Design
[P] Figure 4. Supabase-native payment and settlement flow.
[P] The customer-facing amount is always derived server-side from the stored Pandit price snapshot, selected Samagri/Prasad lines, configured live-service charges and applicable fees.
[P] Razorpay secrets and webhook verification run only in Edge Functions.
[P] Each provider event must have an idempotency key/provider event identifier; duplicate webhooks must not create duplicate payment transactions or duplicate payouts.
[P] A booking may have multiple payment orders/transactions because the customer can make an advance and later balance payment.
[P] Refunds reference captured transactions and store the refund amount/policy snapshot used at the time of cancellation.
[P] Payout records are created only after the approved completion/confirmation condition. Platform fee is initially 0% but remains configurable in the schema.
[P] Do not call the customer-to-Pandit flow “escrow” in product/legal copy unless the payment provider and client have explicitly confirmed the legal/technical escrow arrangement.
[P] 12. Kundli & Astrology Implementation
[P] Figure 5. Kundli order and astrology subscription/delivery flow.
[P] 12.1 Kundli
[P] Customer enters required birth details and selects a Pandit.
[P] Server creates a 100% payment obligation and order snapshot.
[P] Payment is verified through the Razorpay Edge Function.
[P] Pandit receives the paid order and prepares the handwritten Kundli.
[P] Pandit uploads the scanned PDF into the private Kundli Storage bucket.
[P] Customer accesses the PDF through an authorized signed URL.
[P] Customer confirmation or authorized completion action makes the Pandit payout eligible.
[P] 12.2 Astrology subscription
[P] Admin configures plan name, duration and price in astrology_subscription_plans.
[P] Customer purchase creates an astrology_subscriptions row linked to a payment_order.
[P] Daily in-app and weekly WhatsApp content is stored as astrology_content and linked to subscriber delivery records.
[P] Cron creates/dispatches delivery work; Queues provide retries for failed asynchronous delivery.
[P] WhatsApp provider credentials live only in Edge Function environment secrets.
[P] Auto-renewal is not assumed until the client explicitly approves it.

[P] 17. Explicitly Out of Scope Unless Separately Approved
[P] AI-generated Kundli/astrology engine.
[P] Automated planetary/Kundli calculation engine beyond the approved handwritten-Kundli workflow.
[P] Complex temple-management ERP.
[P] Customer referral/loyalty program.
[P] Digital Dakshina/tipping unless separately approved.
[P] Pandit commission/fee logic beyond the current 0% platform-fee assumption.
[P] Separate Financial Admin / Service Admin roles; Phase 1 has Admin and Super Admin unless the client explicitly adds sub-roles.
[P] Large-scale video storage/recording platform; live video is delegated to an external provider.
[P] Any feature appearing only in the old blueprint but not in the approved Phase 1 scope.

1. Architecture Decision

This revision supersedes the earlier ERD implementation assumption that migrations would be generated from Drizzle. The entity model remains relational, but the execution model is Supabase-native.

Client applications: React Native mobile apps, customer-facing website and Admin web portal.

Authentication: Supabase Auth.

Database: Supabase PostgreSQL.

Normal data access: Supabase client/PostgREST under RLS.

Atomic business operations: PostgreSQL functions/RPCs called through authenticated server/client flows as appropriate.

Privileged and third-party operations: Supabase Edge Functions with server-side secrets.

File storage: Supabase Storage with private buckets and signed URLs for sensitive documents.

Realtime: Supabase Realtime; durable state lives in PostgreSQL. Prefer Broadcast for ephemeral events and avoid subscribing to every table change.

Scheduled work: Supabase Cron.

Reliable asynchronous work: Supabase Queues for retryable/background processing.

Geospatial filtering: PostGIS for Pandit service areas and customer-location matching.

Migrations: Supabase SQL migrations managed with the Supabase CLI and committed to Git.

The older product blueprint proposed Fastify and Drizzle, but this document intentionally replaces that implementation choice. The final Phase 1 business behavior remains the controlling requirement.

2. Supabase-Native System Architecture

Figure 1. Supabase-native Kashi Veda domain architecture.

2.1 Runtime responsibilities

Frontend clients may read/write only through authenticated Supabase APIs and RLS-protected operations.

Client applications must never contain a Supabase service-role key, Razorpay secret, WhatsApp credential, live-provider secret or payout credential.

Price calculation, booking confirmation, refunds, payout eligibility and other money/state transitions must be validated server-side in PostgreSQL functions and/or Edge Functions.

PostgreSQL remains the source of truth for booking and payment state; client UI state is never authoritative.

Storage paths and signed URLs are controlled by database authorization rules; customers and Pandits only receive files they are entitled to access.

6.3 Realtime, Cron and Queues

Realtime Broadcast: use for ephemeral booking/availability/live-session UI events where subscribers need immediate updates but the event itself is not the source of truth.

Postgres Changes: use selectively for durable notification badge updates or narrowly scoped state changes; do not subscribe every client to high-churn tables.

Cron: daily subscription deactivation, scheduled astrology generation/delivery, reminders and housekeeping.

Queues: retryable WhatsApp/push delivery, batch astrology delivery, deferred payout work and other asynchronous jobs.

The database remains authoritative even when a realtime or queue message is delayed or duplicated; consumers must be idempotent.

8. PostGIS / Pandit Location Matching

Pandit service areas are stored as normalized location records and/or PostGIS geography values.

Customer home-visit booking validates that the selected Pandit serves the customer location before a slot can be confirmed.

A Pandit may be shown publicly as “Currently Unavailable” even when the profile remains visible; availability and service-area checks are separate concerns.

A booked slot is excluded from future availability blocking so a Pandit cannot accidentally make an existing booking unavailable.

Spatial indexes should be added for the chosen geography columns if radius-based search is used.

11. Money, Payment and Payout Design

Figure 4. Supabase-native payment and settlement flow.

The customer-facing amount is always derived server-side from the stored Pandit price snapshot, selected Samagri/Prasad lines, configured live-service charges and applicable fees.

Razorpay secrets and webhook verification run only in Edge Functions.

Each provider event must have an idempotency key/provider event identifier; duplicate webhooks must not create duplicate payment transactions or duplicate payouts.

A booking may have multiple payment orders/transactions because the customer can make an advance and later balance payment.

Refunds reference captured transactions and store the refund amount/policy snapshot used at the time of cancellation.

Payout records are created only after the approved completion/confirmation condition. Platform fee is initially 0% but remains configurable in the schema.

Do not call the customer-to-Pandit flow “escrow” in product/legal copy unless the payment provider and client have explicitly confirmed the legal/technical escrow arrangement.

12. Kundli & Astrology Implementation

Figure 5. Kundli order and astrology subscription/delivery flow.

12.1 Kundli

Customer enters required birth details and selects a Pandit.

Server creates a 100% payment obligation and order snapshot.

Payment is verified through the Razorpay Edge Function.

Pandit receives the paid order and prepares the handwritten Kundli.

Pandit uploads the scanned PDF into the private Kundli Storage bucket.

Customer accesses the PDF through an authorized signed URL.

Customer confirmation or authorized completion action makes the Pandit payout eligible.

12.2 Astrology subscription

Admin configures plan name, duration and price in astrology_subscription_plans.

Customer purchase creates an astrology_subscriptions row linked to a payment_order.

Daily in-app and weekly WhatsApp content is stored as astrology_content and linked to subscriber delivery records.

Cron creates/dispatches delivery work; Queues provide retries for failed asynchronous delivery.

WhatsApp provider credentials live only in Edge Function environment secrets.

Auto-renewal is not assumed until the client explicitly approves it.

18. Development Gate

The team should now treat this document as the Supabase-native database and backend implementation baseline. Before generating the first migration, the lead developer should verify naming, nullability, foreign keys, indexes, RLS feasibility and state-transition rules.

1. Review the 40-table relational model.

2. Approve the Supabase-native architecture and remove Drizzle/Fastify from Phase 1 implementation tickets.

3. Finalize the remaining configurable business values listed in Section 16 before enabling production payment/refund behavior.

4. Create SQL migrations under supabase/migrations and run them against a dedicated development project.

5. Implement RLS, RPCs, storage policies, Edge Functions, Realtime channels, Cron and Queues before building sensitive frontend actions.

6. Generate Supabase TypeScript database types for frontend/backend type safety.

7. Only after database/security tests pass, proceed to the production booking, payment and payout integrations.
